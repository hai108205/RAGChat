# Production RAG Pipeline Design

**Status:** Approved architecture direction — implementation pending specification review

## Goal

Replace the split Web/Rocket.Chat RAG implementations with one production-grade pipeline that makes ingestion idempotent, retrieval grounded and observable, and migration safe for existing chats.

## Scope

The design covers backend document ingestion, Qdrant indexing, retrieval, context construction, grounded generation, citations, history handling, telemetry, and typed failures. Existing HTTP and Rocket.Chat callback contracts remain compatible during migration.

Out of scope: agent/tool orchestration, OCR for image-only PDFs, a new reranker provider, and deleting legacy collections before rollout evidence supports it.

## Constraints and principles

- Correctness, retrieval quality, observability, maintainability, then performance.
- Postgres is the source of truth for document/index manifests; Qdrant is the query index.
- A vector may only be searched with an embedding generated by the identical model and dimension profile.
- Source citations are selected and validated by application code, never invented by the model.
- No raw secrets or full sensitive document/prompt bodies are logged by default.
- Every new behavior is introduced test-first and deployed behind a compatible read/write transition.

## Target architecture

```text
HTTP / Rocket.Chat input
        |
        v
RagIngestionService
  Parse -> Normalize -> Enrich -> Split -> Validate -> Version
       -> Embed -> Upsert -> Persist manifest
        |
        v
Postgres manifest <----> Qdrant versioned embedding-profile collection

Conversation + user message
        |
        v
RagAnswerService
  History window -> optional query rewrite -> retrieve candidates
  -> deduplicate/diversify -> rerank (when enabled) -> context budget
  -> grounded generation -> verified citations -> persistence/response
```

The Web routes and Rocket.Chat worker are adapters. They call common services rather than own parsing, chunking, embedding, retrieval, prompt, or citation logic.

## Data model and indexing

Add a document manifest and a chunk manifest (or extend the present source/page models where migration analysis confirms it is safe). A manifest records source identity, content hash, version, active state, ingestion lifecycle, embedding profile, collection identifier, and timestamps.

Every chunk carries deterministic metadata:

```text
documentId, parentDocumentId, chunkId, chunkIndex, contentHash, version,
source, fileName, documentType, page, slide, sheet, section, heading, chatId,
workspaceId, roomId, threadId, ingestionTimestamp, embeddingProfile
```

`chunkId` is derived from source/document identity, version, structural locator, chunk index, and normalized content hash. Repeating the same document/version therefore performs upserts rather than creating duplicate vectors.

Collections are named by immutable index version and embedding profile, not randomly per document. Qdrant payload filters enforce source and tenant scope. A new embedding model or dimension creates a separate profile collection; no vectors of different dimensions share a collection.

Scope is an explicit discriminated contract, never a set of optional filters. `web` retrieval requires the owning `chatId`, which is stored and payload-indexed on every Web chunk. `rocketchat` retrieval requires normalized non-empty `workspaceId` and `roomId`; when `threadId` is present it may read that thread and room-level documents (`threadId = null`), while a room-only request may read only room-level documents. Cross-room, cross-workspace, and global search require an explicit authorization policy and a distinct `global` scope. Missing required scope values fail closed before querying Qdrant.

Ingestion is a resumable saga:

1. Register or reuse the document version and create an `INGESTING` run.
2. Parse and validate source segments.
3. Generate embeddings in configured provider-safe batches with retryable errors distinguished from permanent errors.
4. Upsert deterministic points.
5. Atomically mark the manifest/index run active after all expected chunks exist.
6. On failure, retain an actionable failed run; compensate only the points known to belong to that version.

## Parsing and chunking

The parser returns structured segments rather than one flattened text string where source structure exists.

| Document type | Segment boundary | Split behavior |
| --- | --- | --- |
| Markdown | heading hierarchy | heading-aware sections; keep fenced code blocks intact |
| HTML / crawled web pages | DOM heading/section | remove boilerplate, retain heading path and canonical URL |
| PDF | page | preserve page number; recursively split within page/section |
| DOCX | heading/paragraph where available | preserve heading path; recursive fallback |
| XLSX / CSV | sheet and rows | retain sheet and header context; avoid mixing unrelated rows |
| PPTX | slide | retain slide number and title |
| Plain text | paragraph | recursive token-aware splitting |

Chunk limits are typed configuration, expressed in tokens. Defaults are benchmark candidates rather than fixed architectural constants. Chunk validation rejects empty, duplicate, oversized, and metadata-incomplete chunks. The first rollout benchmarks a small/medium/large token profile against a labelled retrieval set before selecting defaults.

## Retrieval and answering

Retrieval has these deterministic stages:

1. Load a bounded, coherent conversation window separately from retrieval.
2. Produce a retrieval query. Use the original message for standalone questions; invoke a structured query-rewrite only for detected follow-ups or ambiguous references.
3. Retrieve a configurable candidate pool with strict Qdrant metadata filters and the corresponding embedding profile.
4. Remove duplicate chunks and apply source/section diversity. MMR is enabled when a result set is near-duplicate-heavy.
5. Apply the existing lexical grounding rerank as baseline. A cross-encoder is an optional adapter only after an offline quality evaluation justifies its cost.
6. Build bounded context deterministically. Include source labels, structural metadata, and canonical citation IDs.
7. Generate an answer under grounded instructions, then persist the answer-to-selected-source mapping.

The model receives system instructions, selected retrieval context, conversation history, and current message as distinct message units. It must state that evidence is insufficient when no grounded context is selected. It may cite only IDs supplied in context; application code maps those IDs to returned sources.

The response citation contract is application-owned: each selected context source has one canonical citation ID, and the response `sources` array is generated directly from that selected set, with duplicate IDs removed and no unselected source permitted. Streaming text cannot create, modify, or promote a citation. If a client displays model citation markers, it must render only markers already present in the response `sources`; malformed, duplicate, and unknown markers are presentation text, not citations. Claim-level citation extraction is deferred until a non-streaming structured-output contract is introduced and tested.

Conversation history is never embedded wholesale. A token-aware history window preserves recent user/assistant turn pairs. When LangChain model integration is introduced, use the documented `trimMessages` path with `startOn: "human"`; do not use ad-hoc array slicing.

## LangChain.js adoption

The installed packages are `@langchain/core` 1.1.36 and `@langchain/textsplitters` 1.0.1. The current backend does not declare `langchain` or an official chat-provider integration, so it must not import `initChatModel` or LCEL until matching packages and their type contracts are added deliberately.

When introduced, LangChain is used where it adds a verified capability:

- `Document` and official splitter implementations for normalized chunks.
- `trimMessages` for bounded message history.
- `initChatModel` plus the matching official provider integration for provider-neutral non-streaming/rewrite operations.
- Zod-backed `withStructuredOutput` for query analysis/rewrite where provider support is verified.
- Official tracing callbacks/LangSmith only behind configuration flags.

Raw OpenAI streaming remains behind a generation adapter until the LangChain integration preserves provider behavior and token usage. No legacy agent executor APIs or hand-written JSON extraction parsers are introduced.

## Observability and failures

Every ingestion and answer run has a `ragRunId`, propagated from request/job IDs. Structured logs and metrics record stage, duration, provider/model/profile, batch count, candidate count, selected chunk IDs, score distribution, and retry count. Detailed context/prompt content is opt-in, redacted, and access-controlled.

Metrics are low-cardinality counters/histograms for each stage: parse, normalize, split, embed, index, rewrite, retrieve, rerank, context build, and generation.

Typed errors preserve their stage and retryability, including `INVALID_DOCUMENT`, `EMPTY_DOCUMENT`, `PARSER_FAILURE`, `CHUNK_VALIDATION_FAILURE`, `EMBEDDING_FAILURE`, `VECTOR_STORE_FAILURE`, `NO_GROUNDED_CONTEXT`, `QUERY_REWRITE_FAILURE`, `MODEL_TIMEOUT`, `MODEL_RATE_LIMIT`, and `MODEL_PROVIDER_FAILURE`.

## Migration and rollback

1. Add schema/index manifest support without altering legacy reads.
2. Write contract, unit, integration, and retrieval-quality tests first.
3. Dual-write new document versions to the versioned index while legacy write behavior remains enabled.
4. Dual-read resolves coverage per eligible document version, not merely per scope. It queries v1 for versions whose v1 manifest is active and queries legacy only for eligible versions without one; it then unions and deduplicates results by source/version provenance. A scope/profile is marked fully covered only after every active legacy-eligible document version has an active v1 manifest. An empty or low-confidence v1 retrieval is a grounded no-result, not a legacy fallback. A v1 runtime failure is surfaced as a v1 failure by default; a temporary availability fallback requires an explicit flag and emits `legacy_fallback_reason` telemetry.
5. Backfill legacy sources in checkpointed batches; report failures by document/version.
6. Compare retrieval quality, citation validity, error rate, and latency before defaulting reads to v1. The release owner approves cutover only when: scope-isolation tests have zero leaks; citation source validity is 100%; Recall@10 is at least the legacy baseline on the labelled evaluation set; MRR@10 is no worse than 5% below baseline; v1 retrieval error rate is no higher than baseline plus 0.5 percentage points; and p95 retrieval latency is no higher than 25% above baseline for the same load profile. The evaluation set must include at least 50 labelled queries per supported corpus type before a default-read decision.
7. Disable legacy writes, preserve rollback read flag through a retention window, then delete old collections only through the existing cleanup outbox.

Rollback is a feature-flag read switch to the legacy retriever. No destructive Qdrant cleanup is allowed until backfill, quality gates, and retention requirements are met.

## Acceptance criteria

- Re-indexing an unchanged document/version creates zero duplicate vectors.
- All returned chunks have complete traceable metadata and a stable citation mapping.
- Query embedding always matches the searched embedding profile/dimension.
- Room/workspace filtering is enforced at retrieval and verified by tests.
- Follow-up questions retrieve based on a rewritten contextual query when needed.
- Context fits the configured budget deterministically, with no duplicate chunks.
- Every failed run identifies the stage, code, and retryability without logging secrets.
- Metrics and trace logs reconstruct the full RAG decision path for an authorized debug run.
- Existing Web and Rocket.Chat contracts pass regression tests during dual-read migration.
